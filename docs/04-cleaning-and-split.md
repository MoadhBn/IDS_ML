# 04 - Cleaning and splitting the data

This phase turns the two raw files into the three sets every model will use: training, validation and test. The problems behind each decision are described in [03 - First look at the data](03-first-look-at-the-data.md). This page explains what we did about them, in which order, and why the order matters.

The code is in `src/data.py` (cleaning and splitting) and `src/preprocessing.py` (encoding). Section 2 of the notebook calls these functions and shows the counts at each step, in French, as part of the report.

## The order of operations

1. Load the two official files.
2. Clean each file on its own: drop `id`, remove duplicates, remove contradictory rows.
3. Remove from the test file every flow that already appears in the training file.
4. Split the cleaned training file into training (80 %) and validation (20 %).
5. Leave encoding and scaling to the model pipelines, so they are learned on training data only.

The order is the point. Duplicates are removed before any split, because removing them after would leave copies of the same flow on both sides of the split, which is exactly the leak we are trying to avoid. The course's own list of pitfalls mentions this one by name. The test set is cleaned with the same rules as the training set, and after step 3 we never look at it again until the final results.

## Step 2: cleaning

### Dropping `id`

`id` is only the row number, and the rows are sorted so that the label follows the order. In the training file, the first quarter of the ids contains no attacks at all and the last quarter contains nothing but attacks. A model given this column would learn where the row sits in the file. We drop it. The notebook shows the proportion of attacks per quarter so the jury can see why.

### Duplicates

We call two rows duplicates when all 42 features and the label are identical. We keep the first and drop the others. Note that we ignore the attack family here: if two rows are the same flow with the same label but were filed under two different families, they still teach the model the same thing.

This definition finds a few more duplicates than the one in doc 03, which also compared the family. With it, 74,072 rows are removed from the training file and 28,380 from the test file. That is 42 % and 34 % of the files. The proportions are large but not unusual for this dataset: many attacks were generated by replaying the same tools, so they produce identical flows.

### Contradictory rows

After removing duplicates, 229 feature vectors in the training file still appear twice, once as normal and once as an attack. Since the model only sees the features, it cannot be right on both. Keeping them would only add noise and penalise every model in the same way. We remove both rows of each pair, 458 rows in total. The test file has 6 such vectors (12 rows), removed in the same way.

The training file goes from 175,341 to 100,811 rows, and the test file from 82,332 to 53,940.

## Step 3: removing the overlap with training

1,300 rows of the cleaned test file have exactly the same features as some row of the training file. We compare on features only, whatever the label, because what matters is whether the model has already seen this input. A model could get those rows right by memory, so the test would partly measure memory instead of generalisation. We remove them, which leaves 52,640 test rows.

We compare against the raw training file rather than the cleaned one. It is the stricter choice: a row that was only dropped from training as a duplicate is still a flow the authors put in the training data.

This is the one choice that makes our numbers harder to compare with papers that use the raw files. We accept it and will state it in the report. If the jury asks, the notebook can give the score with and without these rows in one line.

## Step 4: training and validation split

The partition files have no time columns, so the chronological split the course asks for when data is timestamped is not possible here. We keep the authors' separation: their test file, cleaned, is our test set.

The cleaned training file is cut into 80 % training and 20 % validation with scikit-learn's `train_test_split`, seed 42. The split is stratified on the attack family. Stratifying means each family keeps the same share on both sides. Without it, a family as small as Worms (121 rows after cleaning) could end up almost entirely on one side. Since "Normal" is one of the families, the share of attacks is kept as well, 48.8 % on both sides.

What each set is for:

- **Training** fits the models, and hyperparameters are tuned on it by cross-validation, as the course requires.
- **Validation** compares the tuned models and is where we will choose a decision threshold.
- **Test** is used once, at the very end, for the numbers we report.

The final sizes are 80,648 training flows, 20,163 validation flows and 52,640 test flows. The notebook checks that no feature vector is shared between any two of the three sets. All three checks return zero.

## What cleaning did to the class balance

Before cleaning, attacks were 68.1 % of the training file and 55.1 % of the test file. After cleaning they are 48.8 % and 36.1 %. Most of the duplicates were attacks, especially in the Generic family, which falls from 40,000 training rows to 3,924. Replayed attack traffic produces identical flows much more often than normal traffic does.

The test set still does not look like the training set. It has much more normal traffic (64 % against 51 %), fewer Exploits and Fuzzers, and a little more Generic. This gap comes from the authors' files, not from our cleaning. The figure `reports/figures/familles_apres_nettoyage.png` shows it, and we will have to keep it in mind when the test scores come in. For PR-AUC in particular, the reference level of a random model is now about 0.36 on the test set, against 0.49 on validation.

## Step 5: encoding, kept for the models

The three text columns are turned into numbers by one-hot encoding: one column per possible value, set to 1 for the value the flow has. `proto` alone has 133 values, so the 42 features become 192 columns.

The encoder is built with `handle_unknown="ignore"`. The test file contains two `state` values (`ACC` and `CLO`) that never appear in training. Without this option the encoder would crash on them. With it, an unknown value simply gets zeros in every `state` column.

Numeric features are standardised (rescaled to mean 0 and standard deviation 1) only for logistic regression, which is sensitive to the scale of its inputs. Trees are not. Keeping the raw values for the random forest and XGBoost has a real benefit for this subject: the SHAP explanations will then be in real units ("sttl = 254", "sbytes = 1,200"), which an analyst can read.

The encoder is not fitted here. It is placed inside each model's scikit-learn `Pipeline` in the next phase, so it is refitted on the training folds of every cross-validation round and never sees the validation or test data. The notebook only fits it once at the end of section 2 to check that it runs on the test set without error.
